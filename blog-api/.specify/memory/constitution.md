# ブログAPI プロジェクト憲章

## コア原則

### I. セキュリティファースト

すべての設計・実装においてセキュリティを最優先事項とする。

- 入力値バリデーションは必須（MUST）とし、すべてのユーザー入力を検証する
- JWT認証を使用し、トークンの有効期限・署名検証を厳格に行う
- パスワードは必ず（MUST）bcrypt等の安全なハッシュアルゴリズムで保存する
- SQLインジェクション、XSS、CSRFなどOWASP Top 10脆弱性への対策を必須（MUST）とする
- 機密情報（APIキー、パスワード等）は環境変数で管理し、コードにハードコードしない（MUST NOT）
- すべてのセキュリティイベント（認証失敗、認可エラー等）をログに記録する（MUST）

**根拠**: ブログAPIは認証情報やユーザーデータを扱うため、セキュリティ侵害は
ユーザーの信頼を損ない、法的責任を招く可能性がある。

### II. 明確なエラーハンドリング

予測可能で一貫性のあるエラーレスポンスを提供する。

- すべてのエラーレスポンスは統一されたJSON形式を使用する（MUST）:
  ```json
  {
    "error": {
      "code": "ERROR_CODE",
      "message": "ユーザー向けメッセージ",
      "details": {}
    }
  }
  ```
- エラーコードは一意の識別子とし、ドキュメント化する（MUST）
- 内部エラーの詳細（スタックトレース等）をクライアントに公開しない（MUST NOT）
- 想定外のエラーはすべてキャッチし、500エラーとして適切に処理する（MUST）
- エラーログには十分なコンテキスト情報を含め、デバッグを容易にする（SHOULD）

**根拠**: 明確なエラーハンドリングはAPI利用者の開発効率を向上させ、
運用時のトラブルシューティングを容易にする。

### III. APIバージョニング

APIの後方互換性を管理し、安定したインターフェースを提供する。

- すべてのエンドポイントはURLパスにバージョンプレフィックスを含める（MUST）: `/api/v1/`
- 破壊的変更は新しいメジャーバージョンで導入する（MUST）
- 非推奨となったエンドポイントは最低6ヶ月の移行期間を設ける（SHOULD）
- 非推奨エンドポイントはレスポンスヘッダー `Deprecation` で警告する（SHOULD）
- バージョン間の移行ガイドをドキュメント化する（MUST）

**根拠**: 適切なバージョニングにより、既存クライアントを破壊することなく
APIを進化させることができる。

### IV. HTTPステータスコード

HTTP標準に準拠したステータスコードを一貫して使用する。

- 成功レスポンス:
  - `200 OK`: 取得・更新成功
  - `201 Created`: リソース作成成功
  - `204 No Content`: 削除成功
- クライアントエラー:
  - `400 Bad Request`: リクエスト形式エラー
  - `401 Unauthorized`: 認証必要
  - `403 Forbidden`: 認可エラー
  - `404 Not Found`: リソース不存在
  - `409 Conflict`: 競合（重複など）
  - `422 Unprocessable Entity`: バリデーションエラー
- サーバーエラー:
  - `500 Internal Server Error`: 予期しないエラー
- ステータスコードとエラーメッセージは必ず（MUST）一致させる

**根拠**: 標準的なHTTPステータスコードの使用により、API利用者は
レスポンスを直感的に理解でき、エラーハンドリングが容易になる。

### V. OpenAPIドキュメント

APIの完全なドキュメントを自動生成し、常に最新の状態を維持する。

- OpenAPI 3.0仕様に準拠したAPI定義を維持する（MUST）
- Swagger UIを `/api-docs` エンドポイントで提供する（MUST）
- すべてのエンドポイント、パラメータ、レスポンスをドキュメント化する（MUST）
- リクエスト・レスポンスの例を含める（SHOULD）
- ドキュメントは実装と同期させ、乖離がないようにする（MUST）
- 認証方法を明確に記載する（MUST）

**根拠**: 正確で最新のAPIドキュメントは開発者体験を向上させ、
サポートコストを削減する。

### VI. テストカバレッジ

高品質なコードを維持するため、包括的なテストを実施する。

- コード全体のテストカバレッジは80%以上を維持する（MUST）
- ユニットテスト: 個々の関数・メソッドの動作を検証する
- 統合テスト: API エンドポイントの動作を検証する
- 新機能追加時は対応するテストを必ず（MUST）作成する
- テストはCI/CDパイプラインで自動実行する（SHOULD）
- カバレッジが基準を下回るPRはマージしない（SHOULD）

**根拠**: 高いテストカバレッジはリグレッションを防ぎ、
リファクタリングを安全に行える環境を提供する。

## 技術スタック

本プロジェクトで使用する技術スタックを定義する。

| カテゴリ | 技術 | 備考 |
|---------|------|------|
| ランタイム | Node.js | LTS バージョンを使用 |
| フレームワーク | Express.js | RESTful API構築 |
| データベース（開発） | SQLite | ローカル開発・テスト用 |
| データベース（本番） | PostgreSQL | スケーラビリティ確保 |
| 認証 | JWT | アクセストークン・リフレッシュトークン |
| ドキュメント | OpenAPI 3.0 / Swagger | API仕様書自動生成 |
| テスト | Jest | ユニット・統合テスト |

**設計原則**:
- RESTful設計原則に準拠する（MUST）
- リソース指向のURL設計を採用する
- 適切なHTTPメソッドを使用する（GET: 取得、POST: 作成、PUT/PATCH: 更新、DELETE: 削除）

## 開発ワークフロー

開発プロセスにおける品質ゲートを定義する。

### コードレビュー要件

- すべてのコード変更はプルリクエストを通じて行う（MUST）
- プルリクエストは最低1名のレビュアーによる承認を必要とする（SHOULD）
- セキュリティに関わる変更は追加レビューを必須（MUST）とする

### 品質ゲート

1. **静的解析**: ESLint によるコード品質チェックをパスする（MUST）
2. **テスト実行**: すべてのテストがパスする（MUST）
3. **カバレッジ確認**: テストカバレッジ80%以上を維持する（MUST）
4. **ドキュメント確認**: API変更時はOpenAPI定義を更新する（MUST）

### ブランチ戦略

- `main`: 本番環境にデプロイ可能な安定版
- `develop`: 開発中の機能を統合するブランチ
- `feature/*`: 新機能開発用ブランチ
- `fix/*`: バグ修正用ブランチ

## ガバナンス

### 憲章の優先度

この憲章はプロジェクトのすべての開発活動において最上位の指針となる。
個別の判断に迷う場合は、この憲章に立ち返って判断を行う。

### 改訂手順

1. 改訂提案はプルリクエストとして提出する
2. すべてのチームメンバーによるレビューを受ける
3. 承認後、バージョン番号を更新する:
   - MAJOR: 原則の削除または根本的な再定義
   - MINOR: 新しい原則やセクションの追加
   - PATCH: 文言の明確化、誤字修正
4. 依存するテンプレートとの整合性を確認する

### コンプライアンス確認

- 各プルリクエストにおいて、この憲章への準拠を確認する（MUST）
- 定期的に（四半期ごと）憲章の有効性をレビューする（SHOULD）
- 原則からの逸脱が必要な場合は、明確な理由を文書化する（MUST）

### ドキュメント言語

すべての仕様書・計画・タスク・実装に関するドキュメントは日本語で記述する（MUST）。
