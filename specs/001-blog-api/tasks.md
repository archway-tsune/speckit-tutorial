# タスク一覧: ブログ記事管理API

**入力**: `/specs/001-blog-api/` の設計ドキュメント
**前提条件**: plan.md（必須）、spec.md（必須）、research.md、data-model.md、contracts/

**テスト**: 本プロジェクトではテストカバレッジ80%以上が要件のため、各ユーザーストーリーにテストタスクを含む。

**構成**: タスクはユーザーストーリーごとにグループ化され、各ストーリーを独立して実装・テスト可能。

## フォーマット: `[ID] [P?] [ストーリー] 説明`

- **[P]**: 並列実行可能（異なるファイル、依存関係なし）
- **[ストーリー]**: 対象ユーザーストーリー（例: US1, US2, US3）
- 説明には正確なファイルパスを含む

## パス規約

- **単一プロジェクト**: リポジトリルートに `src/`, `tests/`
- パスは `blog-api/` からの相対パス

## 依存関係と実行順序

### フェーズ依存関係

- **セットアップ（フェーズ1）**: 依存なし - 即時開始可能
- **基盤（フェーズ2）**: セットアップ完了に依存 - すべてのユーザーストーリーをブロック
- **ユーザーストーリー（フェーズ3以降）**: すべて基盤フェーズ完了に依存
  - 並列実行可能（チーム体制の場合）
  - または優先度順に順次実行（P1 → P2 → P3）
- **仕上げ（最終フェーズ）**: 必要なユーザーストーリー完了に依存

### ユーザーストーリー依存関係

- **ユーザーストーリー1（P1）**: 基盤完了後に開始可能 - 他ストーリーへの依存なし
- **ユーザーストーリー2（P1）**: 基盤完了後に開始可能 - US1と並列実行可能だが、テストでUS1の認証機能を使用
- **ユーザーストーリー3（P2）**: 基盤完了後に開始可能 - US2で作成した記事を表示
- **ユーザーストーリー4（P2）**: 基盤完了後に開始可能 - US2で作成した記事を更新・削除
- **ユーザーストーリー5（P3）**: 基盤完了後に開始可能 - US3の機能を拡張

### 各ユーザーストーリー内の順序

1. テストを先に書き、失敗することを確認
2. モデルを実装
3. サービスを実装
4. コントローラーを実装
5. ルーティングを設定
6. テストがパスすることを確認

### 並列実行の機会

- セットアップ内の[P]タスクはすべて並列実行可能
- 基盤内の[P]タスクは並列実行可能
- 各ユーザーストーリー内のテストタスク[P]は並列実行可能
- 異なるユーザーストーリーは（チーム体制であれば）並列実行可能

## 実装戦略

### MVP優先（ユーザーストーリー1, 2のみ）

1. フェーズ1: セットアップ完了
2. フェーズ2: 基盤完了（重要 - すべてのストーリーをブロック）
3. フェーズ3: ユーザーストーリー1完了
4. フェーズ4: ユーザーストーリー2完了
5. **停止して検証**: 登録→ログイン→記事作成のフローをテスト
6. デプロイ/デモ可能

### インクリメンタルデリバリー

1. セットアップ + 基盤完了 → 基盤準備完了
2. ユーザーストーリー1追加 → 独立テスト → デプロイ/デモ（認証MVP）
3. ユーザーストーリー2追加 → 独立テスト → デプロイ/デモ（記事作成）
4. ユーザーストーリー3追加 → 独立テスト → デプロイ/デモ（記事閲覧）
5. ユーザーストーリー4追加 → 独立テスト → デプロイ/デモ（記事編集）
6. ユーザーストーリー5追加 → 独立テスト → デプロイ/デモ（検索/フィルタ）
7. 各ストーリーが価値を追加し、以前のストーリーを壊さない

## メモ

- [P]タスク = 異なるファイル、依存関係なし
- [ストーリー]ラベルは特定のユーザーストーリーへのトレーサビリティ
- 各ユーザーストーリーは独立して完了・テスト可能
- 実装前にテストが失敗することを確認
- 各タスクまたは論理グループ完了後にコミット
- 任意のチェックポイントで停止してストーリーを独立検証可能
- 避けるべき: 曖昧なタスク、同一ファイルの競合、独立性を損なうストーリー間依存
